*스킬이 무엇인지, 내가 만든 스킬, 써 본 기록과 만들 때 정한 규칙을 한 장에 모은 마인드맵.*

## 1. 스킬이 무엇인가

Claude Code 공식 문서는 스킬을 이렇게 설명한다. `SKILL.md` 파일에 지시를 적어 두면 Claude가 그것을 도구 상자에 넣고, 필요할 때 쓰거나 사용자가 `/스킬이름` 으로 직접 부를 수 있다. 문서는 같은 지시를 채팅에 계속 붙여 넣고 있다면 스킬로 만들 때라고 권한다.

![[IT 트렌드/첨부/스킬 만들기/concept-skill-loading.png]]
*개념도. 스킬 폴더의 구성과 각 부분이 읽히는 때. Claude Code 공식 문서 내용을 바탕으로 직접 그렸다.*

`SKILL.md` 는 두 부분으로 나뉜다. 맨 위 `---` 사이의 앞머리에는 이름과 설명을 적고, 그 아래 본문에는 할 일의 순서를 적는다. 문서에 따르면 앞머리 항목은 모두 선택이고, 설명 하나만 적기를 권한다. Claude는 이 설명을 보고 스킬을 쓸지 정한다.

스킬이 읽히는 때도 나뉜다. 평소에는 설명만 목록에 올라 있고, 스킬을 부르면 본문이 대화에 들어와 작업이 끝날 때까지 남는다. 본문이 가리키는 참고 문서는 필요할 때만 읽고, 스크립트는 내용을 읽지 않고 실행만 한다. 그래서 긴 참고 자료를 넣어 둬도 쓰기 전까지는 거의 비용이 들지 않는다. 문서는 `SKILL.md` 를 500줄 아래로 유지하고 자세한 내용은 따로 빼라고 권한다.

스킬은 놓는 자리에 따라 범위가 달라진다. 내 모든 프로젝트에 쓰려면 개인 폴더(`~/.claude/skills`)에, 한 저장소에서만 쓰고 함께 나누려면 그 저장소의 `.claude/skills` 에 둔다. 이름이 같으면 기업 설정, 개인, 프로젝트 순으로 앞선 것이 쓰인다.

## 2. 왜 지금 스킬인가

![[IT 트렌드/첨부/스킬 만들기/result-skill-repo-stars.png]]
*에이전트 스킬 저장소의 GitHub 별 수. 2026년 11월 7일 GitHub API로 직접 조회했다.*

스킬을 모아 공개한 저장소가 큰 관심을 받고 있다. 11월 7일 기준으로 개인 개발자 mattpocock이 자기 작업 폴더에서 꺼내 공개한 `mattpocock/skills` 가 별 31.7만 개로, Anthropic 공식 저장소 `anthropics/skills`(18.8만 개)보다 많다. Cloudflare의 보안 감사 스킬과 Google의 제품별 스킬 저장소도 각각 6.5만, 2.3만 개다.

별 수로 알 수 있는 건 관심의 크기까지다. GitHub 가짜 별을 다룬 연구는 의심스러운 별을 약 600만 개 찾았다. 남이 만든 스킬은 별 수보다 `SKILL.md` 를 직접 읽어 보고 고르는 게 낫다.

## 3. 내가 만든 스킬

| 스킬 | 하는 일 | 구성 |
|---|---|---|
| nyuri-post | 글 형식, 그림 도구, 점검, 게시 | `SKILL.md` 68줄과 형식 문서, 그림 지침, 마인드맵과 점검과 게시 스크립트 |
| nyuri-weekly-trend | 여섯 분야 동시 조사, 별점 기준, 보고서 형식 | `SKILL.md` 71줄과 조사 지시문 틀, 별점 기준, 보고서 형식 |
| nyuri-it-trend-routine | 위 두 스킬과 다른 스킬을 순서대로 부르는 입구 | `SKILL.md` 53줄 한 장 |

루틴 스킬은 직접 일을 하지 않는다. 단계마다 어떤 스킬을 부르고, 무엇이 되면 끝났다고 보는지만 적는다. 실제 규칙은 각 스킬의 참고 문서에 있다. 그래서 "IT 트렌드 루틴 돌려줘" 한 마디로 조사부터 게시까지 같은 순서가 반복된다.

외부 스킬도 함께 쓴다. 글쓰기와 마케팅 검토 스킬, 한국어 AI 티를 빼는 스킬, 마인드맵과 도식 스킬 같은 것들이다. 볼트의 스킬 31개 중 22개가 외부에서 가져온 것이다. 저장소를 받아 `SKILL.md` 를 먼저 읽고, 실행 코드가 없는 것만 설명서와 참고 문서를 복사했다. 라이선스와 출처 파일도 같은 폴더에 남겨 뒀다.

## 4. 써 본 기록

![[IT 트렌드/첨부/스킬 만들기/workflow-pipeline.png]]
*루틴 스킬이 단계마다 부르는 스킬. 위 줄은 단계, 아래 줄은 그 단계에서 쓰는 스킬이다.*

이틀 동안 스킬 폴더를 바꾼 커밋이 20번이었고, 그중 15번이 11월 7일 하루였다. 대부분 피드백을 규칙으로 옮긴 커밋이다. 첫 주간 글을 올린 뒤 받은 피드백은 이렇다.

- 제목에 "별점표"를 쓰지 말 것
- 마인드맵 아래 요약 표와 별점 기준 절은 빼고, 기준은 한두 문장으로만
- 표의 출처 열 이름은 조사용 말 대신 그냥 "출처"로
- 의견 상자 제목은 "뉴리의 생각"
- 그림이 AI스럽다. 대칭 상자와 무지개 색을 빼고 블로그 색으로

이런 말을 채팅으로만 주고받으면 다음 글에서 같은 실수를 한다. 그래서 피드백을 받을 때마다 형식 문서의 "사용자 피드백" 목록에 한 줄씩 적었다. 지금 그 목록에는 규칙이 9개 있다. 그림 피드백은 따로 그림 지침 문서가 됐다. 블로그 바탕색과 글꼴, 강조색은 한 그림에 하나, 그림 안에는 제목을 넣지 않는다는 내용이다. 이 글의 그림도 그 지침으로 그렸다.

막힌 곳도 있었다.

- 작업 중에 만든 루틴 스킬을 바로 부르자 "Unknown skill"이 났다. 공식 문서를 보니 Claude Code가 변경을 바로 알아채는 스킬 폴더는 개인 폴더, 지금 연 프로젝트의 `.claude/skills`, `--add-dir` 로 더한 폴더였다. 그날은 볼트보다 한 단계 위 폴더에서 Claude Code를 열었기 때문에 볼트 안의 새 스킬은 그 범위 밖이었다. 볼트 폴더에서 다시 열면 된다.
- 외부 스킬을 설치 스크립트로 바로 받으려 하자 Claude Code 자동 모드가 외부 코드 실행이라며 막았다. 그래서 저장소를 받아 읽고 파일만 복사하는 방식으로 바꿨다. 지금 생각하면 이쪽이 맞다.
- 범용으로 쓰는 조사 스킬 하나에는 특정 업종을 전제로 한 맥락 문단이 들어 있었다. 공개 블로그 조사에 그대로 쓰면 글에 맞지 않는 관점이 섞인다. 그 스킬은 출처 신뢰도 기준만 빌리고 맥락 문단은 쓰지 않는다고 루틴 스킬에 적었다.

## 5. 스킬을 만들 때 정한 규칙

- 설명에는 언제 쓰는지를 먼저 쓴다. Claude가 보고 고르는 건 설명뿐이고, 문서에 따르면 목록에서는 일정 길이가 넘으면 잘린다.
- `SKILL.md` 에는 순서와 기준만 두고, 형식과 예시는 참고 문서로 뺀다.
- 피드백은 받은 자리에서 파일에 적는다. 다음 세션의 Claude는 이번 대화를 기억하지 못한다.
- 비밀번호, 금지어 목록 같은 것은 스킬 폴더 안에서도 깃에 올리지 않는 하위 폴더에 둔다.
- 남이 만든 스킬은 별 수가 아니라 내용을 읽고 고른다. 실행 코드가 들어 있으면 무엇을 하는지 먼저 본다.

## 6. 아쉬운 점과 확인할 점

- 스킬 본문은 부르면 대화에 남아 작업 내내 자리를 차지한다. 문서에 따르면 대화가 길어져 요약될 때는 스킬마다 앞부분 5,000토큰만, 전체 25,000토큰 안에서 다시 붙는다. 루틴처럼 여러 스킬을 부르는 긴 작업에서는 오래된 스킬 내용이 빠질 수 있다.
- 스킬은 지시일 뿐 강제가 아니다. 규칙을 적어 둬도 모델이 놓칠 수 있어서, 금지 기호와 금지어 같은 것은 따로 점검 스크립트로 막는다.
- 스킬 파일을 고치면 그동안 쓴 글과 형식이 어긋날 수 있다. 이번에도 첫 글을 고친 뒤 형식 문서를 다시 맞췄다.

> [!note] 뉴리의 생각
> 1. 스킬은 프롬프트 모음보다 작업 기록에 가깝다. 실수하고 피드백을 받은 자리가 그대로 규칙으로 남는다. 6개월 뒤에도 이 블로그의 스킬 파일이 처음 모습에서 거의 바뀌지 않았다면 이 생각은 틀렸다.
> 2. 앞으로 스킬 저장소는 별 수보다 "누가 실제로 매일 쓰는 스킬인가"로 평가받을 것이다. 개인 작업 폴더에서 꺼낸 저장소가 공식 저장소보다 별이 많은 것도 그 신호로 본다.

## 용어 정리

| 용어 | 뜻 |
|---|---|
| 스킬 | 할 일의 순서와 기준을 적은 `SKILL.md` 와 참고 문서, 스크립트를 묶은 폴더 |
| 앞머리(frontmatter) | 파일 맨 위 `---` 사이에 적는 이름, 설명 같은 속성 |
| 볼트 | 옵시디언에서 노트를 모아 두는 폴더 |
| 자동 모드 | Claude Code가 명령을 실행하기 전에 위험한 동작을 스스로 걸러 내는 실행 방식 |
| 토큰 | 모델이 글을 읽고 쓰는 단위. 대화에 들어갈 수 있는 양이 정해져 있다 |
