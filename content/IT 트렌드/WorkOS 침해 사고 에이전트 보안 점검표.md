> [!abstract] 한 줄 요약
> 보안 연구자가 성능 시험을 돌리던 AI 해킹 에이전트가 격리된 시험 환경을 벗어나 인증 서비스 회사 WorkOS의 내부 도구를 침해했다. WorkOS는 인터넷에 열린 옛 도구, 운영까지 넘어온 개발용 자격 증명, 속도 제한이 없는 API, 늦은 탐지를 원인으로 꼽았다. 같은 네 가지 기준으로 이 블로그의 저장소를 점검해 봤다.

## 1. 무슨 일이 있었나

![[IT 트렌드/첨부/WorkOS/concept-detection-gap.png]]
*WorkOS 공지의 날짜를 따라 그린 사고 경과. 첫 접근부터 발견까지 5일이 걸렸다.*

10월 25일, WorkOS의 영업용 내부 도구에 누군가 처음 무단으로 접근했다. 10월 30일 고객 관리 시스템 조회가 갑자기 늘어난 것을 직원이 알아챘는데, 그때는 이미 기록을 대량으로 가져간 뒤였다. WorkOS는 그날 바로 이 도구의 외부 접근을 끊고, 연결된 서비스의 자격 증명을 모두 폐기하거나 바꿨다. 다음 날에는 회사가 직접 만든 내부 도구 전체를 네트워크 경계에서 막았다.

11월 2일 첫 공지를 내고 고객에게 알렸다. 그 직후 한 보안 연구자가 먼저 연락해 왔다. ARTEX라는 공격용 AI 프레임워크로 사이버보안 성능 시험을 돌리던 중 에이전트가 "격리된 시험 환경을 벗어나" 의도치 않게 WorkOS에 접근했다는 내용이었다. WorkOS와 외부 포렌식 회사는 연구자가 낸 요청 기록과 시각을 자사 로그와 맞춰 보고 이 연구자가 맞다고 확인했다. 연구자는 가져간 데이터를 모두 지웠고 누구와도 나누지 않았다고 밝혔다.

노출된 것은 영업과 고객 지원 시스템의 데이터였다. 고객사 담당자 이름과 연락처, 계정과 거래 이력, 영업 통화와 지원 대화와 고객 Slack 대화의 요약이나 일부, 제품 사용 정보가 여기에 들어간다. 일부 지원 대화에는 최종 사용자의 이메일 주소도 있었다. 기록이 몇 건인지는 공개하지 않았다.

## 2. 왜 눈여겨보나

이번 사고가 다른 침해 사고와 갈리는 지점은 침해한 주체다. 시험용으로 돌리던 에이전트가 실험실 밖으로 나가 실제 회사의 데이터를 가져갔다고 피해 회사가 공식 공지에 적었다.

에이전트가 쓴 도구도 가벼운 연구용이 아니다. BleepingComputer는 ARTEX가 한국 은행을 겨냥한 공격, 그리고 네덜란드 취약점 공개 기관(DIVD)과 관련해 이름이 오른 적이 있고, CrowdStrike가 중국 사이버 첩보 조직 Vapor Panda의 약 200개 조직 대상 캠페인에서 이 프레임워크를 확인했다고 전했다. WorkOS는 11월 3일부터 바로 이 도구로 자사 인터넷 노출 시스템을 정기적으로 시험하고 있다.

## 3. 어떻게 뚫렸나: WorkOS가 밝힌 빈틈 네 가지

문제의 도구는 보안 기본값이 강화된 새 플랫폼으로 아직 옮기지 못한 옛 내부 플랫폼에 있었다. WorkOS는 "이 통제들이 있었다면 사고를 줄이거나 아예 막을 수 있었다"고 적었다.

| 빈틈 | WorkOS가 밝힌 내용 | WorkOS가 한 조치 |
|---|---|---|
| 인터넷 노출 | 접근 통제가 너무 느슨해서 내부 도구의 API가 인터넷에서 닿았다 | 10월 30일 해당 도구의 외부 접근 차단, 31일 내부 도구 전체를 네트워크 경계에서 차단 |
| 약한 자격 증명 | 개발용 약한 자격 증명이 운영 환경까지 올라가 있었고, 예측할 수 있는 값이라 에이전트가 주소를 찾은 뒤 바로 인증했다 | 그 인증 경로를 없애고 연결 서비스 자격 증명 전체를 폐기하거나 교체. 개발용 비밀이 운영에 못 올라가게 막는 통제를 추가하는 중 |
| 속도 제한 없음 | 요청 수 제한이 없어 기록을 빠르게 대량으로 가져갈 수 있었다 | 내부 도구의 비정상 접근과 요청량 알림을 추가하는 중 |
| 탐지 공백 | 10월 25일부터 30일까지 모니터링이 활동을 잡지 못했다 | 11월 2일 내부 도구 네트워크 기록을 한곳에 모으는 것 확인, 3일부터 ARTEX로 외부 노출 시스템 정기 시험 |

네 가지 모두 AI라서 생긴 빈틈은 아니다. 사람 공격자였어도 같은 곳을 노렸을 것이다. 차이는 에이전트가 쉬지 않고 주소를 찾고 값을 넣어 본다는 데 있다. 사람이 미뤄 둔 정리 작업이 그만큼 빨리 드러난다.

## 4. 써 본 기록: 내 저장소를 같은 기준으로 점검했다

2026년 11월 7일, 이 블로그를 만드는 저장소 두 개를 WorkOS의 네 가지 기준으로 점검했다. 하나는 블로그 저장소(공개)이고, 하나는 글을 쓰는 옵시디언 볼트 저장소(비공개)다.

| 빈틈 | 확인한 것 | 결과 |
|---|---|---|
| 인터넷 노출 | GitHub 계정의 공개 저장소와 마지막 수정일 | 공개 저장소 12개 중 2개가 1년 넘게 손대지 않은 상태였다. 지금 쓰지 않는 공개 저장소가 WorkOS의 "옛 내부 도구"에 해당한다 |
| 약한 자격 증명 | 두 저장소의 전체 커밋 기록에서 키 모양 문자열과 `.env` 같은 파일 이름 | 키 모양 문자열 32건이 나왔지만 모두 실제 키가 아니었다. `.env` 같은 파일은 0개 |
| 속도 제한 | 외부에서 부를 수 있는 API가 있는지 | 블로그는 정적 사이트라 부를 API가 없다. 해당 없음 |
| 탐지 | 블로그 저장소의 GitHub 보안 기능 | 비밀 키 탐지와 푸시 차단은 켜져 있고 알림은 0건. 의존성 취약점 알림은 꺼져 있었다 |

![[IT 트렌드/첨부/WorkOS/result-secret-scan.png]]
*두 저장소의 전체 커밋 기록에서 찾은 키 모양 문자열 32건을 하나씩 확인한 결과. 직접 실행해 그렸다.*

키 모양 문자열은 정규식으로 찾았다. GitHub 토큰, AWS 키, `sk-` 로 시작하는 AI 서비스 키, Slack 토큰, 개인 키 파일, Google API 키, 그리고 `password = "값"` 같은 대입문이다. 결과를 그대로 믿었다면 키가 32개 새어 나간 줄 알았을 것이다. 하나씩 열어 보니 조사 노트 주소에 들어간 "sk-hynix" 같은 낱말 조각이 16건, 블로그 테마를 만든 원작자가 남긴 설정 예시가 13건이었다. 나머지는 마인드맵 SVG에 들어간 이미지 데이터 조각과 플러그인 코드였다. 검사기를 돌리는 것보다 걸린 것을 하나씩 열어 보는 데 시간이 더 들었다.

에이전트를 가두는 장치도 이번 주에 직접 겪었다. 이 블로그 글을 쓰는 데 Claude Code를 자동 모드로 쓰는데, 작업 중 두 번 실행이 막혔다. 한 번은 외부 저장소의 설치 스크립트를 바로 내려받아 실행하려 할 때였고, 다른 한 번은 저장소의 변경을 되돌려 지우는 명령을 실행하려 할 때였다. 둘 다 내가 맡긴 일의 흐름 안에서 나온 명령이었다. 결국 외부 스킬은 파일을 직접 읽은 뒤 설명서만 복사하는 방식으로 바꿨고, 되돌리기는 하지 않았다. 귀찮았지만 WorkOS 사고를 읽고 나니 그 두 번의 멈춤이 이번 사고의 반대편에 있는 장치라는 생각이 들었다.

## 5. 개인 프로젝트 점검표

WorkOS의 네 가지 빈틈을 개인 개발자가 30분 안에 확인할 수 있는 항목으로 바꿨다.

- [ ] 공개 저장소 목록을 열고 1년 넘게 손대지 않은 것은 보관 처리하거나 비공개로 돌린다
- [ ] 개인 서버나 배포한 서비스 중 인터넷에 열려 있을 필요가 없는 관리 화면과 API를 찾는다
- [ ] 저장소의 현재 파일뿐 아니라 전체 커밋 기록에서 키 모양 문자열을 찾고, 걸린 것은 하나씩 열어 본다
- [ ] 개발용으로 만든 키나 비밀번호가 운영 환경 설정에 그대로 있는지 본다. 있으면 새로 발급하고 예전 것은 폐기한다
- [ ] 직접 만든 API에 요청 수 제한이 있는지 본다
- [ ] GitHub 저장소의 비밀 키 탐지, 푸시 차단, 의존성 취약점 알림을 켠다
- [ ] 코딩 에이전트에 맡길 때 외부 코드 실행과 되돌릴 수 없는 명령은 확인을 거치게 설정한다
- [ ] 에이전트로 보안 시험을 돌린다면 시험 환경이 실제 인터넷과 운영 시스템에 닿지 않는지 먼저 확인한다

## 6. 아쉬운 점과 확인할 점

- 에이전트가 시험 환경을 어떻게 벗어났는지는 WorkOS도 연구자도 밝히지 않았다. 에이전트로 보안 시험을 돌리는 사람에게 가장 필요한 정보가 빠져 있다.
- 몇 건의 기록이 나갔는지 공개하지 않았다. 피해 범위가 영업과 지원 시스템에 그쳤다는 판단은 외부 포렌식 회사가 확인했다.
- 침해 주체는 연구자가 스스로 밝히고 WorkOS와 포렌식 회사가 로그로 맞춰 본 결과다. 연구자가 누구인지와 시험 환경의 구성은 공개되지 않았다.

> [!note] 뉴리의 생각
> 1. 앞으로 비슷한 사고 공지에는 "사람이 했나, 에이전트가 했나"를 가르는 항목이 들어갈 것이다. 이번처럼 접속 프로그램 이름과 요청 패턴을 함께 공개하는 일이 늘 거라고 본다. 내년에도 사고 공지 대부분이 침해 주체를 구분하지 않으면 이 생각은 틀렸다.
> 2. 개인 개발자에게는 새 보안 도구보다 오래된 공개 저장소와 개발용 키를 정리하는 일이 먼저다. 에이전트는 사람이 미뤄 둔 곳부터 찾기 때문이다.

## 용어 정리

| 용어 | 뜻 |
|---|---|
| 에이전트 | 목표를 받으면 스스로 도구를 골라 여러 단계를 이어서 실행하는 AI 프로그램 |
| 샌드박스, 시험 환경 | 프로그램이 바깥 시스템에 닿지 못하게 막아 둔 격리 공간 |
| 자격 증명 | 시스템에 로그인하거나 API를 부를 때 쓰는 키, 토큰, 비밀번호 |
| 속도 제한 | 정해진 시간 안에 받을 수 있는 요청 수를 묶어 두는 장치 |
| 포렌식 | 로그와 흔적을 분석해 사고의 경위와 주체를 밝히는 조사 |
| 푸시 차단 | 비밀 키가 들어간 커밋을 GitHub가 올리기 전에 막는 기능 |
